# 要件定義：LINE × RAG ドキュメントQA Bot

## 1. 概要

### 解決する課題

手元のPDF（マニュアル、仕様書、レシピ集など）の内容を調べたいとき、ファイルを開いて該当箇所を探す手間がかかる。専用のアプリを入れたり、Webサービスにアップロードしたりするのも、日常的に使うには負担が大きい。

普段使っているLINEのトーク画面にPDFを送るだけで内容が検索可能になり、そのまま自然な日本語で質問できれば、この手間がなくなる。

### 実現すること

LINEにPDFを送信すると内容を登録し、テキストで質問すると登録済み文書の内容を根拠に回答するBotを提供する。インストールも会員登録も不要で、操作はすべてLINEのトーク画面で完結する。

---

## 2. 機能仕様

### 2.1 ユーザー操作

| 送信内容 | 動作 |
| --- | --- |
| PDFファイル | テキストを抽出してチャンク分割し、ベクトルDBに登録する。同名ファイルは上書き |
| `一覧` | 登録済みの文書名とチャンク数を返す |
| `削除 <ファイル名>` | 指定した文書を削除する |
| 上記以外のテキスト | 登録済み文書を検索し、その内容を根拠に回答する |

### 2.2 PDF登録フロー

1. LINE Messaging API のWebhookでファイルメッセージを受信する
2. 拡張子とファイルサイズを検証する（PDF以外、10MB超は受け付けない）
3. pdfplumber でページごとにテキストを抽出する
4. ページ単位でチャンクに分割する（1チャンク最大800文字、隣接チャンク間で100文字重複）
5. OpenAI Embeddings API（text-embedding-3-small）でチャンクをベクトル化する
6. ChromaDB にベクトルとメタデータ（ファイル名、ページ番号）を保存する

ページ単位で分割するのは、検索結果から出典ページを復元できるようにするため。チャンクを重複させるのは、境界で文脈が切れて検索精度が落ちるのを防ぐため。

### 2.3 質問応答フロー

1. 質問テキストを受信する
2. 登録済み文書の総文字数を確認する
3. 10万文字以下であれば、ベクトル検索を介さず全文を参考文書としてLLMに渡す
4. 10万文字を超える場合は、質問をベクトル化して類似チャンクを上位20件取得する
5. 参考文書と質問を組み合わせたプロンプトを Claude API に渡し、回答を生成する
6. 回答をLINEに返信する

#### 全文を渡す分岐を設けた理由

上位k件のベクトル検索は、質問の条件が文書中の語と一致しない場合に原理的に弱い。たとえばレシピ集に対する「ワインに合うレシピは？」という質問では、どのチャンクにも「ワイン」という語が出てこないため、類似度の高いチャンクが存在せず、無関係なチャンクがLLMに渡る。

LINEで送られるPDFは多くが数十ページ規模で、全文がLLMのコンテキストに収まる。収まる場合は検索で絞り込まず全文を渡し、取捨選択をLLM側に任せる方が精度が高い。文書が大きい場合のみ検索にフォールバックする。

#### プロンプトの方針

「文書に書かれていない事実を創作しない」ことと、「文書の記述から判断できることは推論する」ことを、別のルールとして明記する。両者を区別せずに「文書の内容だけを根拠に答える」と指示すると、記述の有無を文字列として判定し、材料から料理の特徴を判断するような推論を行わなくなる。

回答には根拠にしたファイル名とページ番号を添えさせ、利用者が元の文書で確認できるようにする。

### 2.4 エラー時の挙動

想定されるエラーを種別ごとに区別し、利用者が次に何をすればよいか分かる文言を返す。

| 発生原因 | 返信内容 |
| --- | --- |
| PDF以外のファイル | 対応形式の案内 |
| 10MB超のファイル | サイズ上限の案内 |
| PDF解析の失敗（破損・暗号化） | 原因の可能性を添えた案内 |
| テキストを抽出できないPDF（画像のみ等） | 抽出できなかったことの案内 |
| 外部API（Embedding / LLM / ベクトルDB）の失敗 | 一時的な障害として再試行を促す案内 |
| 上記以外の想定外のエラー | 汎用の案内 |

アプリ内で発生しうるエラーは `app/exceptions.py` の例外クラスに分類し、ハンドラー側で種別ごとに文言を出し分ける。詳細なエラー内容はログにのみ残し、利用者への返信には含めない。

## 3. システム構成

### 3.1 構成図

```
[ユーザー] → [LINE] → [LINE Messaging API]
                            ↓
                      [Webhook / FastAPI]
                        ↓            ↓
              [PDF受信・テキスト抽出]  [質問受信]
                        ↓            ↓
                 [チャンク分割]    [参考文書の決定]
                        ↓         ↓          ↓
                [Embedding生成]  [全文]  [ベクトル検索]
                        ↓            ↓
                 [ChromaDB保存]  [Claude APIで回答生成]
                                     ↓
                               [LINE返信]
```

### 3.2 技術選定

| カテゴリ | 技術 | 選定理由 |
| --- | --- | --- |
| 言語 | Python 3.12 | RAG関連ライブラリとLLM公式SDKの対応が最も早い |
| パッケージ管理 | uv | 依存解決が高速で、ロックファイルによる再現性が担保される |
| Webフレームワーク | FastAPI | Webhookの受け口として軽量。型ヒントによる検証が標準で入る |
| LLM API | Claude API（Anthropic） | 日本語の応答品質と、長いコンテキストの扱いに強い |
| Embedding | OpenAI text-embedding-3-small | 日本語対応で、次元数とコストのバランスが良い |
| ベクトルDB | ChromaDB | 単一プロセスでファイル永続化でき、別サーバーを立てずに完結する |
| PDF解析 | pdfplumber | ページ単位の抽出が扱いやすく、テーブルを含むPDFにも対応する |
| LINE連携 | line-bot-sdk-python | 公式SDK。署名検証とイベント振り分けを標準で備える |
| ホスティング | Render | GitHub連携で自動デプロイでき、Webhookに必要なHTTPSが標準 |
| Lint / Format | ruff | Lintとフォーマットを単一ツールで完結できる |
| テスト | pytest | 外部APIを差し替えた単体テストに必要十分 |

### 3.3 ディレクトリ構成

```
ask-my-docs-bot/
├── README.md
├── LICENSE
├── pyproject.toml          # 依存定義・ruff・pytestの設定
├── uv.lock
├── render.yaml             # Renderのサービス定義
├── .env.example
├── app/
│   ├── main.py             # FastAPIエントリーポイント（Webhookの受け口）
│   ├── config.py           # 環境変数の読み込み
│   ├── exceptions.py       # エラー種別を表す例外クラス
│   ├── line/
│   │   ├── handler.py      # LINEイベントの振り分けとエラー処理
│   │   └── messages.py     # 返信メッセージ文言
│   ├── rag/
│   │   ├── pdf_parser.py   # PDFテキスト抽出
│   │   ├── chunker.py      # チャンク分割
│   │   ├── embeddings.py   # Embedding生成
│   │   ├── vectorstore.py  # ChromaDB操作
│   │   └── qa.py           # 参考文書の決定と回答生成
│   └── llm/
│       └── claude.py       # Claude APIクライアント
├── tests/
│   ├── conftest.py
│   ├── test_chunker.py     # 分割の境界条件・不正な引数
│   ├── test_pdf_parser.py  # 抽出結果・解析失敗時の例外変換
│   └── test_qa.py          # 参考文書の決定・プロンプトの組み立て
└── doc/
    └── 要件定義_LINE_RAG_QA_Bot.md
```

文言（`messages.py`）とエラー種別（`exceptions.py`）をモジュールとして切り出しているのは、表現の調整とエラー処理の変更を、処理の本体に触らず1箇所で完結させるため。

## 4. 非機能要件

| 項目 | 要件 |
| --- | --- |
| レスポンス | LINE返信まで10秒以内（目安） |
| 対応ファイル形式 | PDF。テキストファイル対応は将来拡張 |
| ファイルサイズ上限 | 10MB（LINE Messaging APIの制限に準拠） |
| 想定規模 | 小規模。単一インスタンス・単一ベクトルDBで動作する構成 |
| シークレット管理 | APIキーは環境変数で管理し、リポジトリには含めない |
| コード品質 | ruff（E / F / I / UP / B）による検査、型ヒント、docstringを前提とする |
| テスト | 外部APIを差し替え、APIキーなしで全テストが実行できる状態を保つ |

## 5. 設計上の制約

実装範囲を限定している箇所と、その理由を明示する。

| 制約 | 内容 | 理由 |
| --- | --- | --- |
| 文書の永続性 | ホスティング環境のファイルシステムが揮発性の場合、再起動で登録済み文書が失われる | ベクトルDBをローカルファイルに置く構成を優先した。外部ベクトルDBへの切り替えで解消できる |
| 利用者の分離 | 登録文書は単一のコレクションで管理し、利用者ごとに分離していない | 小規模利用を前提とした。メタデータに利用者IDを持たせることで対応できる |
| 文書の規模 | 総文字数が10万文字を大きく超えると、検索精度が全文を渡す場合より劣化する | LINEで送られるPDFの規模を前提とした。検索の多段化で改善できる |
